# Self-service signup and subscription access

Public `/signup` is email-first. It stores only a normalized business name/email and a pending registration; it creates no merchant user, workspace or password until email ownership is established. The 24-hour email link opens a form to choose and confirm a password (minimum 12 characters, maximum 72 bytes). Only its explicit POST activates the account. Resend rotates earlier links after a two-minute cooldown. Confirmation locks the registration and rechecks the nonce so repeats cannot create another workspace. Duplicate identities receive generic responses; the initial form never accepts an attacker-chosen password for another email owner.

New owners are signed into the apex overview with a private, unpublished workspace. Password recovery uses a 15-minute single-use link, resets no password on GET and invalidates existing sessions after a successful password change. Pending registrations and suspended accounts cannot use recovery to acquire access. Shared emails across legacy workspaces require the optional workspace slug to select a recovery account.

Email is queued through Sidekiq. Configure `MAIL_FROM`, `SMTP_ADDRESS`, `SMTP_PORT` (default 587), `SMTP_USERNAME`, `SMTP_PASSWORD`, and optional `SMTP_DOMAIN` / `SMTP_AUTHENTICATION`. SMTP verifies TLS. Set `APP_BASE_DOMAIN` to the trusted public platform host; links are built from this setting. The application does not claim to have delivered mail merely because a job was queued. These settings and a running worker are deployment prerequisites.

New self-service workspaces set `subscription_required: true`; the additive migration defaults this flag to false for existing merchants. This preserves the current billing and storefront policy for existing tenants rather than locking them out retroactively.

A flagged workspace has operational access only when `billing_status` is `active` and `billing_period_ends_on` is today or later. A trial, canceled, past-due, missing or expired period does not grant access. Account creation and email confirmation do not activate a paid subscription. Platform super admins retain their existing administrative access.

`Admin::BaseController` checks access after authentication and billing synchronization. Unsubscribed merchants may load the overview and subscription page with GET/HEAD. Every other admin action, including GET forms, is denied before its controller action. HTML/Turbo requests redirect with a subscription prompt; other formats receive HTTP 402 with `subscription_required`. Sign-in/sign-out use the existing separate sessions controller. Subscription access must additionally be enforced by API, provider, and OAuth entry points as described by their integration checks; an admin controller guard alone is not a complete API entitlement policy.

The subscription page exposes only the current merchant's issued, paid or void invoices, with a bounded list and no merchant paid-state mutation. Draft invoices remain internal. Existing platform invoice payment activation (`Invoice#mark_paid!`) updates store billing status and period. No self-service endpoint grants paid access. The existing platform team manually issues and marks invoices paid until an online payment provider and prices are configured. `SUBSCRIPTION_SUPPORT_EMAIL`, if configured with a valid address, enables a contact button on the subscription page; rendering that button sends no message.

Rollback can remove `subscription_required` without changing existing invoices, accounts or store data. Removing the flag removes the new access boundary, so rollback must be an explicit deployment decision.

Focused verification should cover unpaid GET and write denial; overview/subscription access; super-admin and legacy-merchant preservation; active, expired, canceled and past-due periods; API denials; no cross-tenant invoices; and no state changes on rejected requests. Use a dedicated test database and synthetic tenants. Do not activate real paid subscriptions to test this flow.

Authenticated GraphQL, MCP and order-import APIs return HTTP 402 for unsubscribed self-service stores. OAuth authorization prompts for a subscription before granting access. Signed provider order intake verifies its signature before rejecting an unsubscribed store, and makes no writes on rejection. Sendit delivery-status callbacks remain enabled to reconcile parcels already shipped; public tenant checkout is preserved under the existing storefront policy. New self-service stores remain unpublished until paid and explicitly enabled by their staff.

Validation uses a disposable `morea_signup_test` database, queued/test mail delivery and synthetic data. Existing manual access-request administration remains for historical requests; it is no longer the public onboarding path. No real payment or third-party sync is used for verification. The migrations are additive: rollback of registration storage removes pending verification state, and rollback of the session-version column removes password-reset session revocation.
